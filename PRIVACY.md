# NeroSecurity privacy & telemetry disclosure

NeroSecurity includes anonymous error reporting so that crashes and bugs caused by the mod
can be found and fixed. It is **on by default** and **opt-out** (see
[How to opt out](#how-to-opt-out)). This page is the full disclosure required by CurseForge's
moderation rules for mods that use an external analytics/error service, and it documents how
the system is designed to comply with the GDPR (EU) and POPIA (South Africa).

> **Note:** error reporting is **active in official builds** (starting with 0.5.0-beta.1), as
> described on this page, and can be switched off at any time with `telemetryEnabled = false` (see
> [How to opt out](#how-to-opt-out)). A fork or source build that sets `NeroSecurityTelemetry.DSN`
> back to the placeholder value sends **nothing**, ever — no report leaves the machine and no
> network connection is opened, regardless of the settings below. Reports from development
> environments are labelled as such and kept apart from release reports.

## At a glance

NeroSecurity records **who did what, at which of an owner's security devices, and when** — per installation
(a security hub and the devices linked to it). It exists so a base owner can protect their blocks and learn
when someone breaks in.

**It never records:** images or video (a "camera" is a presence sensor; there are no camera feeds), chat,
inventory or chest contents, or where a player walks outside a sensor's cone or beam. Positions in the logs are
always the position of the owner's own device, never of a player.

**Your choices, in game:** `/nerosecurity privacy optout` (stop being named), `/nerosecurity privacy export`
(get a copy), `/neroland data eraseme` (erase). Officers and owners also have the same buttons on a security
hub's **Privacy** tab; everyone has the commands. See
[Your choices](#your-choices-stop-being-named-get-a-copy-be-erased).

## What is collected (error reporting)

When an error **caused by NeroSecurity code** occurs, a report is sent to
[Sentry](https://sentry.io) (hosted in the **EU** — `ingest.de.sentry.io`) containing:

- the stack trace of the error and, for a crash, the error message (scrubbed as described below); for an
  error NeroSecurity caught and recovered from, only the error's type, never its message,
- for an error NeroSecurity caught and recovered from, a short fixed label naming the part of
  the mod and the operation involved (for example `menu_open` plus a menu's translation key) —
  never a player name, UUID, position or any text a player typed,
- a short trail of recent, non-identifying mod activity ("breadcrumbs") leading up to the error,
- the NeroSecurity version, the loader (NeoForge / Forge / Fabric) and its version, the
  Minecraft version, and whether the game is a client or dedicated server,
- the operating system name/version and Java version,
- the list of **other loaded mods** (their public ids and versions only) and how many there are, so a
  crash caused by a mod conflict can be identified,
- a random event ID generated by Sentry for the individual report.

Before anything is sent, your operating-system account name and home-directory path are
replaced with `[user]` wherever they appear — in error messages, log lines, breadcrumbs, and the
file names and paths of stack frames — and anything shaped like a UUID (a player or installation id) is
replaced with `[uuid]`. Absolute file paths of stack frames are removed entirely.

Reports are de-duplicated and hard-capped at 10 events per game session.

## What is NOT collected

- **No IP address** is stored (`sendDefaultPii` is disabled; Sentry discards the sender IP).
- **No username, player UUID, or machine/host name.**
- **No world data, chat, coordinates, inventories, or gameplay analytics** of any kind.
- **No advertising or tracking identifiers** — there is no persistent ID linking reports from
  the same player or machine.
- Errors caused by other mods or by Minecraft itself are filtered out and never sent.

## How to opt out

Set the following in `config/nerosecurity.properties` (created on first launch):

```properties
telemetryEnabled=false
```

This is a client-local switch (not server-synced) and covers everything error reporting sends.
The change takes effect on the next restart of the game or server; nothing is sent while
disabled, and nothing is ever sent before the config — and therefore your choice — has been
loaded.

## Player data

NeroSecurity's security hubs store the data below in the world save (`data/nerosecurity/installations.dat`,
with a last-known-good backup kept by Neroland Core). It exists so the server can decide
who may use a protected block. None of it leaves the server except the hub-screen list described below.

| What is stored | Why | How it is kept small |
|---|---|---|
| Each installation's **owners**, as player UUIDs | an installation must belong to someone | no names are stored |
| Each installation's **members**, as player UUID plus level (MEMBER or OFFICER) | the access decision | no join dates, no names, no last-seen times |
| The installation's **name** (chosen by its owner) and a random installation id | to tell installations apart | the name is cleaned and capped at 32 characters |
| **Positions of the hub and linked devices**, plus each device's block type | to know which blocks an installation controls | positions of the owner's own blocks, never of players |
| **Lockdown state**: on/off, when it started, whether an owner started it, whether a player or an alarm started it, when an alarm lockdown clears itself, and when the last alarm lockdown ended | lockdown, the alarm-lockdown time box and cooldown, and the lockdown-drill milestone | yes/no flags and timestamps instead of who started it |
| When the installation was **created** (a timestamp) | to tell old installations from new ones in operator tools | one timestamp per installation, never per player |
| A random **per-installation secret** (32 bytes) | to sign the installation's keycards, so a forged or edited card is refused | random bytes with no personal content; never sent to clients, logged or reported |
| The **card ledger**: one row per issued keycard with its serial number, level, an encrypted yes/no flag, when it was issued, and — only for a card its writer chose to bind to themself — that player's UUID as the bound owner | to check, on every use, that a presented card was really issued here, has not been revoked or wiped, and (for a bound card) is being presented by its holder | no names; most rows carry no player at all; capped per installation (`keycardsPerInstallation`); a row is deleted when its card is revoked or wiped |
| An installation's **alarm-silence time** (a timestamp), set when its owner silences its alarms from the companion app | so alarms in unloaded chunks stay silent too | one timestamp per installation, no player in it; a lockdown clears it |
| Whether you **opted out of being named** (`data/nerosecurity/privacy.dat`): your player UUID, only if you opted out | so new log rows record you as "anonymous" | nothing else: no time, no name; opting back in deletes the row |
| Your **data export file**, only if you asked for one (`<world>/nerosecurity/exports/<your uuid>.json`) | to give you a copy of your data | deleted after 7 days and by an erasure request; restricted to the server's own user where the file system allows it |

**Keycards.** A keycard item carries only its installation's random id, its level, serial number, encrypted
and bound yes/no flags, when it was issued, a 16-byte signature, and the installation's name as a label —
never a player name or UUID, not even on a bound card (only the ledger above knows its holder). Like any item
data it is sent to the clients of players who can see the stack; "encrypted" hides the level and serial in the
tooltip only. The `/nerosecurity keycards <installation> list` command shows an owner each row's serial, level, flags and age, never a
holder.

**Device events.** Doors, secure chests, keycard programmers and the hub raise security events (for example
door opened, denied or forced; chest opened, changed, denied or forced; keycard written, copied, wiped,
revoked or rejected; device linked or configured). An event carries only its type, the installation id, the
device's position (the owner's own block), the acting player's UUID where there is one, the time and a
severity. A secure chest event records who acted, what kind of thing happened and when — **never what is in
the chest**: no items, counts or slots — and at most one "changed" event per opening; "changed" events from
hoppers and other automation carry no player and are rate-limited. Laser grids and cameras raise "laser
grid tripped" and "motion detected" events for anyone or anything the installation does not permit; players
the installation permits produce no event (unless the server sets `privacyCameraLogsMembers=true`). Events
never leave the server, except as described in "Notifications on your phone" below; they are written to the
audit log below.

- **Pets are judged by their owner, but never logged as them.** A tamed animal is judged by its owner's access
  (a member's dog does not trip the owner's laser). A stranger's pet crossing a beam still raises the event, but
  the row names **nobody**, like a mob's: the pet's owner was not the one sensed and may be nowhere near.
- **Lockdown.** While an installation is in lockdown, everyone except its owners (and server operators) is
  treated as not permitted. Members and officers are then detected and logged by lasers and cameras exactly
  like intruders, with their UUID, for the same retention as any other row. This also applies to a drill.
  Lasers never hurt anyone who has ownership or membership in the installation, even during a lockdown.
- **Operators** pass every sensor and are never logged by one.
- **Beams stay inside the base.** A laser grid node pairs only with another node of the same installation,
  so nobody can stretch an owner's beam out across public ground.
- **What other players' games receive.** Nearby players' games learn only whether a sensor is armed, which
  node a beam runs to, and, after a camera detects something, roughly which way it turns. That direction
  is rounded to 15° steps, updated at most every 2 seconds, and returns to the camera's normal sweep shortly
  after. A sensor's settings, modules and energy are never sent to other players' games.

**Audit log.** Each event above becomes one row in `data/nerosecurity/audit.dat` (with a last-known-good
backup kept by Neroland Core): the event type, the time, the severity, the position of the owner's device,
and the acting player's UUID where there is one. There is no name, no player position, no chest content and
no image: cameras sense presence only. Rows are deleted automatically: after `privacyAuditRetentionDays`
(default **7 days**), presence rows ("motion detected", "member seen by camera") after
`privacyCameraEventRetentionMinutes` (default **60 minutes**), and nothing is ever kept longer than **90
days** whatever the settings say. At most `privacyAuditMaxEntriesPerInstallation` rows (default 500) are kept
per installation; the oldest go first. The log is purged when the server starts, every
`privacyPurgeIntervalMinutes` and before every read. An owner or officer can read their installation's log
with `/nerosecurity log <installation>`; every read is itself recorded as a "log read" row with the reader
as the actor. That command (and **Show who** in the companion app, below) is the only place an *event's actor*
is named (from the server's local name cache, `?` when unknown); the hub's member list, below, shows the
names of an installation's own owners and members. Alarm messages and security monitors name the installation and the kind of event only, never
a player. Alarm messages go to the installation's online owners, and also to its officers only after an
owner runs `/nerosecurity notify-officers <installation> on`. Server owners can switch the log off with
`auditLogEnabled=false`. Dissolving an installation deletes its log.

**Recording notice.** The first time in a session that a player enters the area around an installation that
records anything, they see one action-bar line naming the installation and saying that presence and access
events may be logged. The area is the box around the hub and every linked device, grown by at least the
furthest any camera or laser grid node can sense. It is the largest of `noticeMarginBlocks`, `cameraMaxRange`
and `laserMaxRange`, so everyone a sensor can log is inside it. If a device (a sensor, a door, a chest, a force
field, an alarm, a monitor, or a keycard check) is about to log a player who has not had the notice yet — for
example someone who arrived by teleport and clicked a door at once — the notice is shown first, in the same
moment. The notice cannot be switched off
while anything is logged, and it is not itself logged.

**Shown on screen, never stored:** when an officer or owner opens a hub, the server sends that viewer the
display names and player ids of that installation's own owners and members, looked up from the players online and the
server's local name cache (no internet lookup). Adding a member by name only works while that player is
online. The client forgets this list when the screen closes.

## Your choices: stop being named, get a copy, be erased

**Stop being named (opt-out).** Run `/nerosecurity privacy optout`, or press **Stop naming me** on a hub's
Privacy tab (officers and owners). From that moment on every new audit row about something you do is stored as
"anonymous", for every kind of event except one: the record of **you reading a security log** (in game or with
**Show who** in the app) always names you, because it is the accountability record for seeing other people's
names. Opting out is **not retroactive**: rows recorded before you opted out keep your id until they expire
(at most the retention period below) or you ask for erasure, which removes them at once. **The security event
itself still happens and is still recorded**: a tripped laser is still a tripped laser, a door you were refused
still shows as refused; only who it was is withheld. The log command and **Show who** in the app show
"anonymous" for those rows; hubs, monitors, the app's event list and notifications show every player alike, as
"a player", so they do not reveal who has opted out. Opting out does not hide you from the member list of an installation you belong to
(its owners need that list to manage access), and it does not change whether you may open anything.
`/nerosecurity privacy optin` (**Name me again**) undoes it for future rows; rows stored as anonymous stay
anonymous.
`/nerosecurity privacy status` tells you which applies.

**Get a copy (export).** Run `/nerosecurity privacy export`, or press **Export my data**. The server writes one
JSON file, `nerosecurity/exports/<your uuid>.json` in the world folder, and tells you its path in chat; ask the
server operator for it. It holds everything NeroSecurity keeps about you: the installations you own (with their
hub position and *counts* of co-owners and members), the installations you belong to and your level, the keycard
ledger rows bound to you, every audit row that names you (including rows from before you opted out), whether
you opted out, and the security alerts NeroSecurity raised for you in the companion app (their text, severity,
time and whether you read them). Other mods' alerts are theirs to export. It never contains another player's id or name. You can ask for one export
per minute (`privacyExportCooldownSeconds`); the file is deleted after 7 days.

**Erasure.** NeroSecurity is registered with Neroland Core's shared per-player erasure hook, so one request
removes a player from every Neroland mod: a player can run `/neroland data eraseme`, and an operator can run
`/neroland data erase <uuid>` (Core's inactivity retention sweep uses the same path). For NeroSecurity this
removes the player's member rows everywhere, removes them as an owner, deletes every card-ledger row bound to
them, so any card bound to that player stops working for everyone, and deletes every audit-log row that names
them as the actor. It also deletes their opt-out row, their export file and the server's short-lived memory of
which recording notices they have seen. An installation they owned alone
is not deleted with its blocks; it passes to an anonymous placeholder owner (a "tombstone" that belongs to
no one and grants nothing) and is marked orphaned, so a server operator can dissolve it. If the installation
had other owners, they keep it. An orphaned installation's name is replaced with a neutral one ("Orphaned
installation" and the first characters of its random id), because the name its owner chose may name them; a
co-owned installation keeps its name. Keycard items already in players' inventories keep the old label printed
on them. The backup copy is refreshed straight after, so the erased rows cannot come
back from it.

**Lockdown announcements.** When an installation enters or leaves lockdown, NeroSecurity announces it on
Neroland Core's `nerosecurity:lockdown` threshold channel, which other mods (for example a quest pack) can
listen to. The announcement carries only an opaque installation id and whether lockdown went on or off; never a player, a
name or a position. Residual risk: a mod listening on that channel learns that *some* base entered or left
lockdown. Server owners can switch the announcements off with `lockdownChannelEnabled=false`.

**Milestones.** NeroSecurity also records three personal milestones (first keycard, installation online,
lockdown drill) in Neroland Core's progression store: three yes/no flags per player, keyed by player
UUID, used only to let a quest pack know you reached them. They are never read to decide access. Neroland
Core removes them with the same erasure request described above.

**Force fields and integrations.**

- **Bindings store organisation ids only.** An owner can bind an installation to a NeroFactions faction, a
  NeroColonies colony or a Nerospace station (`/nerosecurity bind`). The installation stores the faction's id, the
  colony's id or the station's number, and the most the binding may grant (MEMBER, the default, or OFFICER, only
  when the owner types it) — never the player who bound it and never a list of the organisation's members.
  Membership is asked of the other mod on the same server each time an access decision is made; it is not copied.
  Only a stored owner of the installation (or a server operator) can bind or unbind; a keycard or another
  integration cannot.
- **What a bound organisation's members can see.** A member of a bound faction or colony (and a bound station's
  current owner) gets access by their rank in that organisation, never above the binding's max level, and so sees
  what that level allows. At MEMBER: the installation's bindings (`/nerosecurity bind <installation>`), including
  whether a binding is suspended, which tells them that no owner is still in that organisation. At OFFICER (a station
  binding always grants its owner OFFICER): also the hub screen, with the installation's owners' and members' display
  names (see "Shown on screen" above), and the audit log.
- **Suspension.** When no owner is still a member of a bound faction or colony, the binding grants nothing until one
  is again. A "faction suspended" or "colony suspended" row is logged at most once per binding per server session; it
  names no player and no organisation.
- **Binding rows.** "Faction / colony / station bound" and "unbound" rows name the owner (or operator) who did it,
  as the actor, like any other audit row.
- **Claims are consulted only to deny.** With Open Parties and Claims installed, NeroSecurity asks it, on the same
  server, whether the acting player may use a protected block at that position, and whether an owner of the
  installation may build where a force field would be placed. A claim can only take access away, never grant it.
  Nothing from the claim mod is stored or logged.
- **Force field passability sync.** Every few ticks, each player within an emitter's range plus 16 blocks is sent
  one yes/no value saying whether **they** may walk through that emitter's field, with the emitter's position, so
  their game predicts the same collision the server decides. It is sent only to that player and never carries
  anyone else's answer, level, name or UUID; their game forgets it on disconnect, and the server never reads it
  back.
- **Field events.** A "force field attacked" row names the attacker by UUID: the player who hit the field, or the
  player who shot a projectile at it (an explosion names nobody). It is logged at most once per attacker per emitter
  every `fieldBreachEventCooldownTicks`. "Force field obstructed" (the field could not place all of its blocks;
  at most once every five minutes per emitter), "overloaded", "collapsed" and "restored" rows name nobody. Every
  field row carries the emitter's position (the owner's own block), never the position of the field block, so it
  never traces where a player stood. They follow the same retention, cap and erasure as every other audit row.
- **Residual.** While an installation is in lockdown its force fields change colour, which anyone within sight
  can see.

## Retention at a glance

| Data | Kept | Setting |
|---|---|---|
| Audit rows | 7 days by default | `privacyAuditRetentionDays` |
| Presence rows (motion detected, member seen by camera) | 60 minutes by default | `privacyCameraEventRetentionMinutes` |
| Rows per installation | 500 by default, oldest first out | `privacyAuditMaxEntriesPerInstallation` |
| Anything logged, whatever the settings | **never more than 90 days** | `privacyRetentionHardCapDays` (can only be lowered) |
| Export files | 7 days | fixed |
| Installations, members, card ledger, opt-out | while the installation (or your choice) exists, until erasure | — |

The purge runs when the server starts, every `privacyPurgeIntervalMinutes` (default 60) and before every log
read. Defaults are deliberately short; a server owner can lengthen retention only up to the hard cap.

## Switching features off

Server owners can switch whole features off in `config/nerosecurity.properties`; each switch is enforced by the
server while the game runs:

| Switch | Effect when `false` |
|---|---|
| `camerasEnabled` | every camera is dark and records nothing |
| `auditLogEnabled` | nothing is written to the audit log; events still drive alarms |
| `forceFieldsEnabled` | no force field projects |
| `lockdownEnabled` | lockdown cannot start and stored lockdowns are ignored |
| `pushNotificationsEnabled` | no companion-app notifications, stored alerts or login summaries |

## Notifications on your phone (NeroLink companion app)

If this server runs the NeroLink bridge and you have paired the NeroLink app and switched the **Security**
notification category on (it is off until you do), NeroSecurity sends you a notification when something
happens at an installation you own — or, if the owner chose "notify officers", one where you are an officer.
Owners and officers are found from the installation's stored member list, never from who is nearby.

**What a notification contains.** Two short lines: what happened and which installation — for example
*"Laser grid tripped"* / *"Orbital Lab (+3 more)"* — and a link that opens that installation in the app.
That is all. It never contains another player's name or id, a position, a dimension, a time other than the
delivery time your phone adds, or anything about what is inside your base. Notifications are grouped: at
most one per installation per minute (`pushCooldownSeconds`), with a count of further events; a lockdown
change is sent at once. The text is visible on a locked phone's screen, which is why it says no more than that.

**Who handles it on the way.** The notification leaves the game server through the NeroLink relay
(`nerorelay.neroserver.xyz`, a service operated for the Neroland community) and is delivered by Google
Firebase Cloud Messaging on Android and Apple Push Notification service on iOS. The relay and these services
are **third-party processors**: they see the two lines above, the notification category (`nerosecurity`), your
app's push token and the server's relay id, for as long as delivery takes. The relay keeps a delivery
cooldown of about a minute per player and category and does not store notification text. Its own retention
and erasure behaviour is described by the NeroLink bridge's privacy notes; NeroSecurity relies on them and
cannot change them.

**What stays on the server.** The same event is also stored as an **alert** in Neroland Core's per-player
alert list (text identical to the notification), so you see it the next time you open the app or log in —
one private chat line with counts only ("3 unread security alerts (2 installations)"). Alerts are removed
when you acknowledge them, after the audit retention period of the installation they describe, when
newer alerts push them out, and by a data-erasure request.

**What the app can see.** When you open the app it reads, over an authenticated connection, the
installations you own or belong to and which dimension each one is in, their devices' status, and recent events as sentences ("Door forced —
Door 2, 4 minutes ago"). Devices are named by kind and number, never by coordinates. Who did something is
shown only as "a player" unless an owner or officer taps **Show who**; that tap is recorded in the
installation's own log as a log read, exactly like reading the log in game, and shows the player's display
name from the server's local cache — never an id. With **Show who**, players who opted out of being named appear
as "a player (anonymous)"; everywhere else in the app (the event list and notifications) every player is just
"a player", so the app does not reveal who has opted out.

**What the app can do.** Acknowledge your own alerts and silence an installation's alarms for a while. Changing
lockdown from the app is **disabled unless the server operator enables it** (`linkLockdownMode`); an operator
can allow clearing a lockdown only, or starting one too, and can require you to be logged in to the game
at the time. The app can never add or remove members, change levels or write keycards.

Switching it off: a server operator sets `pushNotificationsEnabled=false` (no notifications, alerts or login
summaries for anyone on that server) or `linkModuleEnabled=false` (the app sees nothing from NeroSecurity);
you switch the Security category off in the app, or unpair the app.

## Legal basis and your rights (GDPR / POPIA)

The audit log and the sensors' presence events are processed on the basis of the base owner's **legitimate
interest** in knowing who breached their base (GDPR Art. 6(1)(f); POPIA s11(1)(f)), balanced by the recording
notice, by members not being logged by default (members are logged only while their installation is in
lockdown, as described above), by the short retention above, the 90-day ceiling, erasure, and names shown
only on a recorded, privileged read.

Owner rows, the card ledger and milestones are processed because they are needed to provide the feature the
owner chose to use — a protected base only works if the server knows who may open it (GDPR Art. 6(1)(b) and
(f); POPIA s11(1)(b) and (f)). Member rows are processed on the basis of the installation owner's **legitimate
interest** in controlling who may open their blocks (GDPR Art. 6(1)(f); POPIA s11(1)(f)): a member is added by
an officer or owner and may not have chosen anything, so performance of a contract is not relied on for them. They are kept for as long as the installation exists, and removed on an erasure request
or by the server's inactivity retention sweep if the server owner has enabled one.

Companion-app notifications and stored alerts are part of the service the installation's owner chose to use
(GDPR Art. 6(1)(b); POPIA s11(1)(b)); the events they describe are processed under the legitimate interest
stated above.

Error reports are processed on the basis of **legitimate interest** (GDPR Art. 6(1)(f); POPIA
s11(1)(f)): keeping the mod functional and crash-free, using the minimum data necessary. They
are engineered to contain no directly identifying personal information, are stored in the EU,
and are retained only for Sentry's standard retention period before automatic deletion.

The in-game opt-out, export and erasure above are how you exercise your rights to object, of access and to
erasure for NeroSecurity's data on a server; a server's operator is responsible for the data on their server.
To exercise any data-subject right (access, deletion, objection), or with any question about this page, contact
**[info@neroland.co.za](mailto:info@neroland.co.za)** — for a crash report, include the
approximate date/time of the crash so the matching event can be located and removed. Sentry
acts as a data processor for error reports; see
the [Sentry privacy policy](https://sentry.io/privacy/) and
[data processing addendum](https://sentry.io/legal/dpa/).

You also have the right to lodge a complaint with a data-protection supervisory authority: in South Africa the
Information Regulator ([inforegulator.org.za](https://inforegulator.org.za), POPIA s18), and elsewhere the
data protection authority where you live (for the EU, your member state's authority; GDPR Art. 13(2)(d)).

## Changes to this policy

When a future version of NeroSecurity starts storing any further player-attributable data, this
page will be updated **before** that version is released, with the change called out in the
changelog, and that data will be added to NeroSecurity's erasure hook so a single erasure request
purges it alongside every other Neroland mod. Likewise, if a future version ever
collects additional telemetry, this page will be updated before release and the same opt-out
(`telemetryEnabled = false`) will continue to cover everything error reporting sends.
